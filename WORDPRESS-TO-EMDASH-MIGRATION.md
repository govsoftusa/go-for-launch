# WordPress to EmDash on Astro Migration Guide

## Status

Alpha. This path has been exercised once, end to end, on a production news
archive of roughly 3,600 articles, 12,000 media objects and 11,800 public
routes. The lessons below are reproducible, but the workflow has not yet been
repeated across enough sites to be called proven in the sense that the Webflow
and static WordPress paths are.

Read [PLATFORM-MIGRATION-FRAMEWORK.md](PLATFORM-MIGRATION-FRAMEWORK.md) first.
This document is the WordPress-to-EmDash adapter for that framework and does not
restate it.

## Why This Path Differs From WordPress to Static Astro

The existing WordPress workflow in this toolbox assumes the target is a static
Astro site whose content lives in the repository. EmDash changes three
assumptions that the rest of the workflow was built on.

| Assumption in the static path | What EmDash does instead |
|---|---|
| Content is files in the repo, so it is diffable and versioned by git | Content is rows in a database, seeded once and edited thereafter through an admin panel |
| Every route is known at build time, so `getStaticPaths` enumerates them | The site runs `output: "server"`; routes resolve per request |
| Rich text is Markdown or MDX | Rich text is Portable Text, a structured JSON format |
| Pagination is computed over a known array | Pagination is keyset-based with opaque cursors |

Each difference produces work that the static path does not have. The rest of
this document is that work.

## Track 0: Audit the Source Before Extracting

Do this before anything else. See
[SOURCE-COMPROMISE-AUDIT.md](SOURCE-COMPROMISE-AUDIT.md).

A migration copies content out of a system nobody has audited recently. Long-
lived WordPress installations are a common compromise target, and a migration
backup is exactly the artefact that carries an infection into a clean stack, or
that lets an agent unknowingly publish an attacker's markup into a new CMS.
The audit is short and it is not optional.

## Track 1: Extract to a Neutral Dataset

Do not extract straight into EmDash. Extract into the intermediate model the
framework defines, then convert. Two stages instead of one buys three things:
the extraction is re-runnable when the conversion is wrong, the dataset can be
diffed between runs, and the same dataset feeds the parity verifier that has to
independently know what the source served.

`scripts/wp-extract.mjs` reads a WordPress database directly and emits:

```text
dataset/
├── site.json          Settings, permalink structure, counts
├── posts.ndjson       One record per post, with resolved HTML and SEO metadata
├── pages.ndjson
├── media.ndjson       Media library with object-storage locations and variants
├── categories.json
├── tags.json
├── authors.json
├── menus.json         Menus with hierarchy and resolved destinations
├── redirects.json     Legacy plugin rules plus structural rules
└── reports/
    ├── shortcodes.json
    ├── embeds.json
    ├── duplicates.json
    ├── skipped.json
    ├── missing-assets.json
    └── unsupported.json
```

### Read the database, not the WXR export

EmDash ships a WXR importer in its admin panel and it works. It is the wrong
tool for a migration held to this toolbox's standard, for four reasons.

1. It is interactive. A migration that cannot be re-run from a script cannot be
   rehearsed on staging and repeated on production.
2. WXR omits the media offload mapping, which on any site using an offload
   plugin is the difference between working images and 12,000 broken ones.
3. WXR omits the legacy redirect tables that 404-handling plugins populate.
4. A WXR export of a large archive is generated by the compromised source site,
   which Track 0 has just told you not to trust more than necessary.

Use WXR for a small blog. Read the database for anything with an archive.

### Reproduce `wpautop`

WordPress stores Classic Editor content with blank lines for paragraph breaks
and applies `wpautop()` at render time. Extracted content that skips this step
renders as one continuous block. The reference implementation is in the
extractor; the block-element list matters more than the regex.

### Inventory shortcodes before deciding what to do with them

Every shortcode is source-platform behaviour that will not exist in the target.
Count them first. In the reference migration the distribution was:

| Shortcode | Uses | Disposition |
|---|---|---|
| `caption` | ~7,900 | Rendered to `<figure>` and `<figcaption>` |
| `contact-form` | tens | Replaced with a marker element the target binds a form component to |
| `gallery` | single digits | Rendered to a grid of figures |
| `youtube`, `embed` | single digits | Rendered to a lazy iframe |

One shortcode accounted for 99 percent of usage. Handle that one properly and
the rest is a short tail.

### Do not strip bracketed prose

A naive residual-shortcode stripper matches `[his]`, `[sic]` and `[Chicago]`
inside quotations and silently deletes them, corrupting the article. Strip only
a known list of shortcode names, plus unknown names that carry `key="value"`
attributes. Leave everything else as literal text and record it.

## Track 2: Resolve Media Through the Offload Table

This is the single highest-consequence step, and the one most likely to be got
wrong without a specific check.

When a site uses an offload plugin, the URLs stored in `post_content` are the
**pre-offload local paths**. The plugin rewrites them at render time by looking
up the real object key. Those keys are not the same:

```text
stored in post_content:   /wp-content/uploads/2021/05/photo.jpg
actual object key:         wp-content/uploads/2021/05/19222335/photo.jpg
                                                     ^^^^^^^^
                                          version segment added by the plugin
```

In the reference migration **every one of the roughly 12,000 objects** carried
such a segment. Prefixing a CDN hostname onto the stored path produces URLs
that look entirely correct in a diff and 404 for every image on the site.

The resolution rules:

1. Build a map from each original's stored upload path to the directory its
   object actually occupies, read from the offload plugin's own table.
2. Size variants live beside the original, so the original's directory resolves
   the whole family. Strip `-WIDTHxHEIGHT` and `-scaled` from a filename to find
   its family, then re-attach the requested filename to the resolved directory.
3. Record every reference that resolves to nothing. Those are images referenced
   in article bodies that were never offloaded or were later deleted. They need
   a decision, not a silent pass-through.

Verify by sampling. Take twenty resolved URLs at random, request them, and
require twenty 200s. A migration that ships without this check ships a site
whose images are all broken, and nobody notices until the site is live because
the HTML is perfectly well formed.

### Choose delivery variants deliberately

Original uploads on a long-lived publication are frequently enormous; the
reference archive contained originals over 8,000 pixels wide. Select the
largest **core** WordPress size at or below a delivery ceiling.

Restrict the selection to core sizes: `large`, `medium_large`, `medium`,
`thumbnail`. Any site that has changed themes carries variants generated by
themes it no longer runs, hard-cropped to fixed aspect ratios. Selecting one of
those silently recomposes a portrait photograph into a letterbox, and the
result passes every automated check because the file exists and the dimensions
are consistent.

Report every attachment with no core variant under the ceiling. Those need
thumbnail regeneration on the source before cutover.

## Track 3: Split the Seed From the Bulk Content

EmDash applies `seed/seed.json` on first boot and **inlines it into the build**.
That makes it correct for schema, settings, taxonomies, menus, bylines and a
handful of singular pages, and wrong for an archive.

Split along that line:

| Goes in `seed/seed.json` | Goes in bulk import |
|---|---|
| Collections and fields | Articles |
| Taxonomies and all their terms | |
| Menus | |
| Bylines | |
| Widget areas | |
| Static pages, if there are few | |

The reference site's seed came to roughly 500 KB with 31 categories, 6,700 tags,
61 bylines and 7 pages. The 3,600 articles would have added tens of megabytes
to every deployment.

### Add migration identity fields

EmDash's collection schema has no field for the originating platform's record
ID, and no `published_at` on content entries, which a dated permalink structure
needs. Add them explicitly:

```json
{ "slug": "legacy_id",     "label": "Legacy WordPress ID", "type": "integer"  },
{ "slug": "legacy_route",  "label": "Legacy Permalink",    "type": "string"   },
{ "slug": "published_at",  "label": "Published At",        "type": "datetime" },
{ "slug": "updated_at",    "label": "Updated At",          "type": "datetime" }
```

`legacy_id` is what makes an import idempotent. Match on it rather than on the
slug: slugs get edited over a site's life, record IDs do not.

`legacy_route` lets the router serve the exact historical permalink without
re-deriving it from a date and a timezone at render time, which is where
off-by-one-day bugs live.

Carry the previous SEO plugin's per-page output into fields as well. It
represents years of editorial decisions and regenerating it from content is a
downgrade.

### Make Portable Text deterministic

The Gutenberg and HTML converters generate random block keys. Random keys mean
two runs over identical input produce different output, which defeats
idempotent imports and makes it impossible to diff two migration runs to see
what changed.

Post-process every converted document, rewriting each key to a hash of the
document identity and the node's position, and remapping `markDefs` references
as you go. Then assert it: run the generator twice and compare checksums. The
reference implementation does this and the two runs are byte-identical.

### Bind images to media records

The HTML converter emits image blocks whose asset reference is the bare URL it
found. Resolve each one against the media library and rewrite the reference to
the media record's identity, keeping the URL alongside it. Without this the CMS
treats every inline image as an opaque external string and editors cannot
manage them after import.

### Bind authentication to the canonical origin

Treat the CMS authentication origin as migration data. Do not assume that
changing the public site URL, canonical metadata, Worker route, or DNS record
also changes the base URL used for authentication messages.

Before retiring a candidate or provider preview hostname:

1. Identify the CMS value used to compose password reset, invitation, and
   magic-link URLs.
2. Set that value to the canonical production origin through a supported CMS
   setting or API.
3. Request one bounded magic link and assert that its scheme and host equal the
   canonical production origin.
4. Register a new passkey from the canonical origin and complete one sign-out
   and sign-in cycle.
5. Keep the prior passkey and candidate access until the canonical credential
   succeeds.

Passkeys are bound to a WebAuthn relying-party identifier. Adding a canonical
URL to a password manager item's website list does not migrate an existing
passkey from a preview hostname. The passkey must be registered again from the
canonical origin.

If the CMS has no supported setter for an initial-setup authentication value,
use the direct database lane only as a documented break-glass repair. Capture a
point-in-time backup, guard the update by both key and expected old value,
require exactly one changed row, read the value back, and preserve a precise
rollback. This exception does not authorize unrelated database edits.

Test content administration in a clean browser before calling the cutover
complete. Privacy tools and content blockers can reject CMS paths that contain
terms such as `api` or `content`. A loaded admin shell is not sufficient. Open
an existing record, observe the exact content request at the server, save a
reversible no-op or reviewed change, and confirm the public route. When the
request never reaches the server, diagnose client filtering before changing
the CMS, database, or application.

When the publication uses a global trailing-slash policy, test the exact
slashless API URLs emitted by the CMS admin. Do not normalize those URLs by
calling middleware continuation with a substituted request unless the
framework explicitly guarantees a fresh route match and repopulated dynamic
parameters. A changed request URL can retain stale route parameters and pass
undefined collection or item identifiers into the CMS.

Prefer a method-preserving temporary redirect when the framework needs a new
request to resolve the canonical slashed endpoint. Verify list, existing-item,
create, save, publish, authors, and trash endpoints. Include at least one POST
or PUT with a disposable local record so the test proves that the redirect
preserves both the method and body.

## Track 4: Bulk Import

There is no headless bulk-import path in EmDash today. `scripts/emdash-import.mjs`
is a reference implementation over the REST API. The properties that matter:

- **Idempotent.** Look up by `legacy_id`, then `PATCH` or `POST`. An interrupted
  run is resumed by repeating the command.
- **Bounded concurrency.** Enough to saturate the API, not enough to trip rate
  limits. Four to eight in-flight requests is a reasonable starting point.
- **Failure capture.** Write failures to a file with status and response body.
  A run that reports "142 failed" and nothing else cannot be acted on.
- **A dry-run and a limit flag.** Rehearse on twenty-five entries before
  committing to several thousand.

## Track 5: Reproduce the Route Model

### Dated permalinks

`/YYYY/MM/DD/slug/` is the most common structure on established WordPress
publications, and every one of those URLs is indexed. Keep it. The alternative
is redirecting an entire archive, which spends link equity for nothing.

EmDash resolves entries by slug alone, so the date segments are decoration from
its point of view. That creates a duplicate-content surface: the same article
answers at every date in history. Validate the requested date against the
entry's publish date and redirect to the canonical permalink on mismatch.

Set `trailingSlash: "always"`. WordPress served trailing slashes and the entire
index carries them.

### Numbered pagination over cursor pagination

EmDash paginates with opaque keyset cursors. That is the right default for
infinite scroll and it cannot serve `/page/212/`, because a reader arriving from
a search result has no cursor and there is no page 211 to walk from.

An established archive has hundreds of such URLs indexed. In the reference
migration the home archive alone had over 360 pages, and the category archives
added nearly a thousand more.

Resolve the archive in two steps instead: read the ordered index once, slice it
to the requested page, then fetch only that page's entries. The index query is
cacheable and the per-page cost does not grow with page depth.

Redirect `/page/1/` and its taxonomy equivalents to the base route. WordPress
served the archive at both addresses; do not inherit the duplication.

Return 404 for a page beyond the end of an archive. An empty page 900 that
answers 200 is a thin-content page a crawler will find and index.

### Reserved slugs

A route model with dated archives and a top-level page route has collisions
waiting in it. A page slugged `2019`, or `page`, or `category`, will shadow or be
shadowed by an archive route. Check for them in the parity verifier and fail the
build, rather than discovering it when a page disappears.

Duplicate slugs across different dates are the same class of problem: EmDash
resolves by slug, so two articles sharing one collapse to a single reachable
entry. This must be resolved before cutover.

## Track 6: Redirects at Scale

Long-lived WordPress sites accumulate a 404-redirect plugin table. Expect
thousands of rules. Cloudflare's static redirect file caps at 2,100.

Three rules for handling the overflow:

1. **Prioritise.** Structural rules first, since each covers a family of URLs.
   Content redirects next. Shortlink forms such as `/?p=123` last: there is one
   per post and few crawlers still hold them.
2. **Spill the remainder into middleware**, matched against a plain object
   before any content query runs. Never silently truncate.
3. **Drop the junk, and record what you dropped.** A 404-redirect plugin records
   every URL that ever 404'd, which on a public site means vulnerability probes.
   Administrators commonly point them at the home page. Carrying those forward
   spends a scarce redirect budget teaching attackers that their probes get a
   301, and dilutes the home page's inbound link profile. A 404 is correct.

Return 410 rather than 404 for `wp-admin`, `wp-login.php`, `xmlrpc.php` and
`wp-json`. A 410 tells a crawler to stop asking. A 404 invites it to retry
indefinitely, and on a site with an eight-year history that is a lot of retries.

## Track 7: Taxonomy Archive Indexation

Tag archives are the characteristic WordPress SEO question. An established
publication commonly carries more tags than articles, most holding one or two
posts, and the standard advice is to treat those as thin content and suppress
them.

**Measure before applying that advice. On the reference migration it was
backwards.**

Search data for that site showed tag archives earning roughly a tenth of the
organic traffic across its best-performing pages, and about ninety percent of
that traffic went to archives holding fewer than three posts. A rule suppressing
archives under three posts would have noindexed almost every tag page that
earned anything. Meanwhile not one category archive appeared in the same set,
despite every category holding well over a hundred posts.

The reason is that post count measures editorial volume and indexation value
depends on search demand. On a publication that covers named people, venues and
productions, tag archives rank for proper nouns. Someone searching a performer's
name wants every mention of that name, and the archive aggregating them is the
complete answer to the query whether it lists one article or twenty.

Recommended process:

1. Pull ranking and traffic data for the `/tag/` path family before deciding
   anything. Search Console is the right source; third-party crawl estimates
   are usable when Search Console access is not available, with the caveat that
   absence of recorded rankings is not evidence of no value.
2. Suppress only genuinely empty archives. They have nothing to show a reader.
3. Treat any broader suppression as a decision the project owner makes with the
   data in front of them, recorded in the project's intentional-differences
   document, not as a default an agent applies.

The duplicate-content concern behind the standard advice is still real, and it
has a better remedy than deindexing. Many WordPress themes render full post
content on archives rather than excerpts, so a single-post tag archive is a
complete second copy of the article. Rendering excerpts on tag archives removes
the duplication without giving up the ranking. Canonicalising a single-post
archive to its article is the other option, and it does give up the ranking, so
it is the weaker choice where the data shows those archives earning.

## Track 8: Theme Port

For a pixel-exact port, vendor the source stylesheet unmodified and keep every
deliberate change in a separate overrides file. The port then stays auditable:
any visual difference is traceable to a listed decision rather than to an edit
buried in a few thousand lines of vendored CSS.

Reproduce the source framework's DOM structure and class names exactly. On a
Genesis site the stylesheet targets `.site-container`, `.site-inner`,
`.content-sidebar-wrap`, `.content` and `.sidebar-primary` directly, and the
body layout class selects the column arrangement. These are load-bearing.

Read the framework's stored settings rather than inferring behaviour from the
rendered page. They record the archive content mode, thumbnail size and
alignment, breadcrumb visibility per template, pagination style, and the entry
meta format as literal shortcode strings. Reproducing those strings gives
byline and category lines that match without guesswork.

Changes that are worth making anyway, all of which belong in the overrides file
and the intentional-differences document:

- Self-host the webfont the theme loaded from a third party.
- Replace the framework's JavaScript menu toggle with a native disclosure.
- Restore focus visibility, which older themes commonly suppress.
- Honour `prefers-reduced-motion`.
- Reserve image aspect ratios, the largest source of layout shift on archives.

## Track 9: Verification

Route parity is the gate this path most needs, because the failure mode is a
route that quietly stopped existing.

`scripts/verify-route-parity.mjs` builds the expected inventory from the
extracted dataset, independently of the running site, and checks it two ways.

Offline, with no deployment: duplicate slugs, reserved-slug collisions, and
inventory totals by route kind.

Online, against a candidate: probe every non-article route plus a deterministic
sample of articles. Probing several thousand article URLs is a load test, not a
check; sample at a fixed stride so two runs cover the same routes.

The standard release gates still apply and are not replaced by any of this:
PageSpeed at 100 across all four categories on mobile and desktop, native iOS
Safari on the Simulator, render sharpness, interface quality, sitemap
verification and post-deployment host verification.

## Known Gaps in This Adapter

Recorded so the next migration does not rediscover them.

| Gap | Impact | Status |
|---|---|---|
| No headless bulk-import API in EmDash | Requires the reference importer over the REST API | Worked around |
| Seed format has no `publishedAt` on content entries | Dated permalinks need an explicit field | Worked around with a schema field |
| Seed format has no field for a source record ID | Idempotent import needs one | Worked around with a schema field |
| Portable Text conversion emits random keys | Non-reproducible output | Worked around with a post-process |
| Cursor-only pagination | Cannot serve deep numbered archive pages | Worked around with an index-and-slice |
| Comment import | Not implemented; counts preserved, bodies not | Open |
| Multi-author bylines | Mapped one WordPress author to one primary byline; co-author plugins untested | Open |
| Scheduled and private post states | Only published content exercised | Open |
| Custom post types and ACF | Not exercised | Open |
| Multisite | Not exercised | Open |
